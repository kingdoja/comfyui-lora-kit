# 总体架构与开发边界

## 当前环境判断

当前目录更像 ComfyUI Desktop 的用户数据目录，存在 `custom_nodes/`、`models/`、`workflows/`、`input/`、`output/`、`user/`，但没有完整 ComfyUI 源码树。开发应采用 ComfyUI 自定义节点扩展方式，而不是改核心代码。

已有自定义节点是 `custom_nodes/comfyui-gpt-image/`，它展示了可复用模式：

- Python 节点通过 `NODE_CLASS_MAPPINGS`、`NODE_DISPLAY_NAME_MAPPINGS` 注册。
- 前端扩展通过 `WEB_DIRECTORY = './web'` 注册。
- 后端 HTTP 接口通过 `PromptServer.instance.routes` 注册。

## 隔离原则

所有新增内容只进入新的目录，不改现有文件：

- 文档：`ninebot_comfyui_dev_docs/`
- LoRA 训练：`custom_nodes/ninebot_lora_training/`
- LoRA 生图：`custom_nodes/ninebot_lora_generation/`
- 资产库：`custom_nodes/ninebot_asset_library/`
- 工作流 JSON：`workflows/ninebot_*`
- 运行数据：`user/ninebot_*` 或每个扩展自己的 `data/`

如果后续确实需要公共能力，不建议一开始就抽公共包；等 3 个任务出现真实重复后，再新增 `custom_nodes/ninebot_common/`，避免提前设计过重。

## 总体形态

设计图里的“多个工作流集成一个节点”不应理解为把所有功能写进一个巨大节点，而是：

- 对用户暴露少量高级节点：训练器节点、生图节点、资产选择节点。
- 每个高级节点内部封装一段稳定子流程。
- 复杂交互通过前端面板和后端接口完成，节点只保留关键参数和可连线输入输出。
- 工作流 JSON 中使用 ComfyUI Group，把预处理、模型加载、采样、保存等部分框起来并标明作用。

## 推荐分层

1. 自定义节点层
   - 定义 ComfyUI 节点输入输出。
   - 负责把参数传给服务层。
   - 返回图片、模型路径、提示词、元数据。

2. 服务接口层
   - 上传素材。
   - 创建训练任务。
   - 查询训练日志和进度。
   - 列表查询资产、LoRA、checkpoint、ControlNet 模型。

3. 前端扩展层
   - 提供更像设计图的上传、选择、生成按钮、快捷提示词按钮。
   - 适合做资产库面板、训练任务面板和生图操作面板。

4. 工作流层
   - 保存可复用 JSON。
   - 用 Group 标注每段作用。
   - 支持研发验收和业务演示。

## 依赖判断

目前本机 `models/controlnet/` 为空，`models/checkpoints/` 只有一个未完成的 `v1-5-pruned-emaonly.safetensors.part`。因此开发文档和节点需要把“模型文件缺失”作为显式状态处理：

- 列表为空时前端提示需要放置模型。
- 生成节点运行前校验 checkpoint、LoRA、ControlNet 是否存在。
- 示例工作流可以先占位，但不能假设模型已经齐全。

## 三个任务的关系

- 资产库是基础设施：上传图片、分类、打标签、生成 caption。
- LoRA 训练消费资产库中的训练集，输出 LoRA 模型和训练报告。
- LoRA 生图消费资产库素材、LoRA 模型、checkpoint 和 ControlNet 模型，输出结果图片和生成参数。

推荐先做资产库最小版本，再做 LoRA 生图，最后接 LoRA 训练。原因是训练链路最依赖数据质量、硬件和第三方训练脚本，风险最高。
